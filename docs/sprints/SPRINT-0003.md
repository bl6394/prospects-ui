## Overview

Sprint 0001 built the single-flow Day Pass checkout; Sprint 0002 brought it to v1.2 parity and added the §4.5 consent set, Pay Page capture, OTP for every buyer, the prospect-wallet save and two email transports. On 2026-09-15 the user confirmed that Design HTML **v4** supersedes v1.2. This sprint changes the existing implementation to v4. It does not rebuild it, does not start the deferred harness lane, and does not turn the mock QR into a door credential.

**What changes.** (1) The catalog's offers reach the browser and the buyer picks one on the identify screen: three v4 cards for Core South ("Gym Floor" 1-day $25, 3-day $60, 5-day $90 — the multi-day prices are provisional fixture data, CF-04), one pre-selected card for Riverside. The selection is stored on the checkout, survives reload and Change, and is the offer the order shell, sidebar, Pass Terms, Pay button, sale, pass and email all use (CR-10). (2) Validity becomes an inclusive club-local range: `validUntil = visitDate + durationDays − 1`, carried on the order, the issued pass, the receipt and the QR payload, rendered "Today – Fri, Sep 11" wherever v4 does; the date label reads "Pass starts on" for multi-day passes (CR-11). (3) Pass Terms read "{label} to {Club}, valid {validity}", template `2026-09.2`, PRD refund sentence unchanged (CR-17). (4) The done page loses its QR; the pass block reads "{label} · {validity}" and "We emailed your pass and door QR code to {masked}. Show it at the door, or just say your name at the front desk."; the on-page Receipt stays (CR-12). (5) The pass email becomes the credential: receipt (number, item, amount, validity, paid with, seller), a server-rendered QR image and a "View your pass" button (CR-12, CR-13, D41). (6) A public, token-addressed BFF route and a UI page at `/signup/pass/:token` render the same pass and QR without cookie, app or login; the token is an HMAC capability over a random id, stored in a credential store with its own lifetime, scoped to one pass, bounded to the pass window + 24 h view-only, revocable, rate-limited, and the page reveals only first name, masked contact, club, pass facts and receipt number/item/amount (CR-13). (7) The "We'll text your pass here on the day." helper goes; the SMS notice and tel attributes stay (CR-14). (8) The identify layout follows v4's `.offers` grid, `.days` line, 32 px price and 1250 / 640 px breakpoints (CR-15). (9) The Core `m@m.com` returning visitor is **Kelly** Reyes (CR-16). (10) The parity inputs are regenerated from v4 (PR-05); the loop is not run.

**What does not change (carried).** Route `/signup/day-pass?club=NNNNN` → `/signup/pass` on completion; opaque `OJ-PASS-SESSION` cookie and server-side `CheckoutStore`; email-only OTP for every buyer with lookup after consumption; §4.5 consent set with `templateVersion`, `renderedHash`, `consentRevision` and the Pay-tap attestation; one consent snapshot per purchase; Pay Page as the only card entry; save default off; UUID `providedId` wallet write behind `STP_WALLET_WRITES`; test hooks only behind `STP_TEST_HOOKS`; purchase order authorize → persist → wallet → sale → issue → deliver, synchronous and idempotent; skeleton sidebar until an order exists; Riverside as the demo default. Rotating QR (§5A item 6) is **not** built (no verifier exists) and is a register row; live re-pricing of an order after verify is not built (v4 has no control; Change or Start again re-selects); a public resend or purchase-discovery surface is not built.

**Corrections recorded.** `OrderRequest.offerId` never existed; FR-P22/P23 are not in PRD v3.4 (CR-13 rests on D41, FR-P15, UC J1 step 6); tel attributes already present; Riverside stays single-offer (the CR list is already corrected). ## Architecture

### 1. Offer selection before an order exists (CR-10)

```
POST /checkouts               → offers[] (catalog order), selectedOfferId, offer (= selected, compatibility), snapshot.offerId
PUT  /checkouts/:id/offer     {offerId, generation}  state ∈ {identify, challenge, verified}, no active purchase
                              → {selectedOfferId, offer, consent, generation}       409 once an order exists
POST /verify | retryLookup    → createOrderShell(catalog, club, record.selectedOfferId ?? offers[0].offerId) inside the store mutation
PUT /order, POST /purchases, POST /checkouts(resume) → consentSetFor(catalog, club, order.offerId, visitDate, now)
```

- `CheckoutRecord.selectedOfferId` — set by the new route, kept by `resetIdentity` (Change), gone with the checkout (Start again creates a new one). `buildSnapshot` exposes `snapshot.offerId`; the UI restores the checked card on reload.
- `requireOffer(catalog, club, offerId)` resolves the named offer from **this club's** catalog or throws; `consentSetFor`, `validatePurchase` and `buildCheckoutResponse` take the order's `offerId` when an order exists, else `selectedOfferId`, else the first offer. A cross-response test pins that a Core checkout with the 3-day pass selected never renders a 1-day Pass Terms sentence on any route (fact 1), asserting label, amount and validity, not only hash agreement. A removed or foreign offer answers a typed 409 with the refreshed set, never a silent fallback to `[0]`.
- **Concurrency.** The offer route requires `generation`; existing routes keep optional-but-checked semantics. Committed offer edits and committed order edits bump `generation` so equal-generation stale writes are refused (fact 9). Directory resolution reads `selectedOfferId` **inside** the same `CheckoutStore.update` that commits the order; a selection arriving between the external lookup and the commit either lands first (the order uses it) or is refused by the state check (409). Races tested: offer vs verify, offer vs retryLookup, offer vs identity reset, order edit vs purchase. UI serializes offer/order writes and holds Continue/Verify/Pay while a selection is pending. The sprint-wide mandatory-generation matrix is a register row, not this sprint.
- `OfferSummary.label` ("1-day pass") is computed server-side from `durationDays`; `CatalogOffer.provisional?: boolean` marks CF-04 prices in the fixture and the capability report only, never in customer copy. The pre-verification sidebar stays the v4 skeleton; no early payable order is invented to show a total.

### 2. Validity, consent templates and revision (CR-11, CR-17)

- `validUntil = addDays(visitDate, durationDays − 1)` — inclusive club-local calendar days (v4 `validityLabel`; FR-P6 calendar-vs-hours and Q19 remain CF-05). Computed in `createOrderShell` and recomputed by `applyOrderUpdate` on every `visitDate` change; `maxDaysAhead` bounds the **start** date; an invalid date is rejected exactly as today (`isVisitDateAllowed`), never clamped. Purchase validation re-checks at authorization, including a midnight rollover.
- Carried on `StoredOrder`, `OrderSummary` (`durationDays`, `label`, `validUntil`), `FinalizeSaleInput`, `IssuePassInput`, `IssuedPass`, `PurchaseResult.pass`, the receipt snapshot, `DeliveryInput`, the mock QR payload (`STP2|passId|club|visitDate|validUntil|sig`, sig over all fields + receipt) and `PassView`.

One-time purchase — no membership, no renewal, no recurring billing."`; `TemplateContext` gains `offerLabel`, `validity`; `CONSENT_TEMPLATE_VERSIONS.passTerms = '2026-09.2'`; refund paragraph unchanged (PRD D15/D22, AD-09). `consentRevisionOf` additionally hashes `commercial:${offerId}|${amountMinor}|${currency}|${visitDate}|${validUntil}` so club-overridden static Pass Terms cannot hide a product or range change (fact 10). ### 3. Receipt snapshot (CR-12, CR-13)

At the ISSUED checkpoint the orchestrator writes an immutable `PurchaseRecord.receipt = {receiptNumber, offerId, item, label, amountMinor, currency, visitDate, validUntil, purchasedAt, seller:{legalName, address?}, paidWith?:{brand, last4}, firstName}`. The pass email, the public `PassView` and the resend read this snapshot, never the checkout or the live catalog (fact 4), so the page works after checkout expiry and after a catalog change. `PurchaseResult.receipt` exposes the customer-safe subset; `paidWith` appears in the email only.

### 4. Pass credential, token and public routes (CR-13, D41, CF-06)

- **Store.** `STP/ports/passCredentialStore.ts` — `PassCredentialStorePort { getOrCreateForPurchase(purchaseId, mint) , findByTokenId(id), rotate(purchaseId, mint), revoke(purchaseId), capability() }`; `adapters/mock/passCredentialStore.ts` process-local. Record: `{tokenId, purchaseId, clubNumber, linkExpiresAt, issuedAt, revokedAt?, rotations}`. Lifetime is the pass window + grace, independent of the checkout sweep (30 min / 2 h). The store is in-memory by declaration (L4); a restart loses links and purchases alike — recorded, not worked around.
- **Token.** `pv1.<id>.<exp>.<sig>`: `id` = 24 random bytes base64url (`newOpaqueId`), `exp` = `linkExpiresAt` epoch seconds, `sig` = HMAC-SHA256 over `pv1|pass-view|id|exp` with a dedicated `STP_PASS_LINK_SECRET` (required whenever the pass routes are mounted; boot guard refuses a missing or short secret outside mock mode), constant-time compare, strict shape regex before any lookup. The token carries no email, member, purchase, receipt or club identifier. Raw tokens leave the BFF only in the pass email, on the creating `POST /purchases` 201 (`pass.viewPath`, attached by the route from the orchestrator's transient return, never written to `result`), in the `pass-link` GET/POST responses to the owning checkout, and in the hooks-only outbox. `GET /purchases/:pid`, `/testing/state` and logs never carry it; the request logger and `historyFallback` debug lines redact `/passes/` and `/pass/` paths; the AppDynamics snippet is not injected for `/pass/` documents.
- **Public routes** (`BFF/routes/shortTermPass/passes.ts`, same router, **no** `checkoutChain`): `GET /passes/:token`, `GET /passes/:token/qr.png`. Chain: `rateLimit(passLimiter per IP, WindowLimiter(60, FIFTEEN_MINUTES_MS))` → token shape → signature → store lookup → revoked / unknown / link-expired → one identical 404 → `requireShortTermPass` with the club resolved from the credential (flag + `onlineProspects`, fail closed) → response. Headers on every response incl. errors: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow`, image `X-Content-Type-Options: nosniff`. GET only, no cookie read or set, no CSRF, no redirects from input. Absolute URLs only from `STP_PUBLIC_BASE_URL` (incl. `/signup`), never the Host header. Turning the club flag off also disables retrieval of an issued pass — recorded as a rollout decision (R13).
- **`PassView`** built by `STP/passView.ts` from the receipt snapshot, the club and club-local `today`: status `upcoming | active | expired`; `qr` present only when not expired; field set pinned by a key-set leak test (U15).
- **Rotate and resend** (`POST …/pass-link`) and **current link** (`GET …/pass-link`) on the owning verified checkout (`loadOwnedPurchase(allowVerifiedMember)` as `wallet-retry`): serialized per purchase; mint → deliver → revoke old **only when the transport accepts**; `WindowLimiter(3, ONE_HOUR_MS)` per purchase; 409 unless issued. Hooks-only `POST /testing/passes/revoke?checkoutId=&purchaseId=` for the smoke's 404 proof.
- **Static QR everywhere (CF-07, §5A item 6).** Email image and page render the issued pass's static `STP2` payload. Rotation, scan freshness, single-visit consumption and a desk verifier are register rows; `PassView.qr.kind` is `'static'` so `'rotating'` can be added without breaking the contract. A revoked link cannot recall a PNG already delivered by email; only a real verifier can reject admission.

### 5. Pass email and QR (CR-12, D41)

- **Renderer:** `STP/qr.ts` — `renderQrPng(payload): Promise<Buffer>` with the `qrcode` package (error correction M, margin 1, scale 6 → ~330 px), payload size bounded. Tests decode the PNG with a test-side decoder (`jsqr`, dev dependency) and compare byte-for-byte to the payload; re-encoding equality is not accepted as proof. `qrcode.react` stays a UI dependency for the pass page only.
- **Template:** `adapters/smtp/templates/passEmail.ts` — `renderPassMail(input: DeliveryInput, image: {kind:'cid', cid} | {kind:'url', url}) → {subject, text, html, attachments?}`, following `email-1-verification-code.html` line for line (header legal name + location, white card, footer with address and Pass Terms / Privacy links, "Sent on behalf of … by ABC Fitness"). Content per U13, absolute dates, a plain View URL line near the top. **No design exists for this email**; it ships PROPOSED to DESIGN (D2).
- **Image strategy (decision):** SMTP → PNG as a nodemailer attachment `cid:pass-qr` (demonstrable in Mailpit; renders in Apple Mail, Gmail, Outlook). Publisher → `<img src="{STP_PUBLIC_BASE_URL}/api/short-term-pass/passes/{token}/qr.png">` because `EmailEngineRequest` has no attachment slot (fact 5). Data URIs never (Gmail and Outlook.com strip them). The hosted PNG exists anyway for the page's `<noscript>` and support.
- **Inputs:** `DeliveryInput` becomes `{channel, destination, checkoutId?, club: ClubMailContext, receipt (snapshot), qrPayload, viewPath}`; `EmailPublisherMailer.deliver` passes `input.club` to `buildEngineRequest` (billing code, display name — fact 5). `MockOutbox` records `label`, `validUntil`, `viewPath` on `kind:'pass'`. Orchestration stays validate → authorize → prospect → wallet → sale/capture → issue → **receipt snapshot + credential mint** → deliver → complete; QR, SMTP or publisher failure stays in `delivery` and never refunds an issued pass; if credential minting fails the pass is still issued, `delivery` is `failed`, no link is advertised, and T3 blocks until fixed. Replay returns the stored result without resending; `wallet-retry` never mints or mails.

### 6. Done page and receipt (CR-12, CR-13)
