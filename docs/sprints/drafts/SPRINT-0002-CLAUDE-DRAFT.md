## Overview

Sprint 0001 shipped a working Day Pass checkout whose screens follow the Riverside demos. The 2026-09-10 sprint review compared that build against the Director of Design HTML v1.2 and the PRD's Round 4 decisions and produced nine build changes, four harness requests and three confirmations. D46 reverses the Sprint 0001 addendum: **v1.2 is now the source of truth** for fonts, sizes, layout, colours and copy; the Riverside demos remain the source only for fixture data (club, product, price, Jordan's contact) and for behaviours v1.2 does not show.

**What changes.** (1) The identify screen becomes email-only with the single catalog offer rendered as a selected offer card, and code entry moves inline (header "Check your email!", read-only email + Change, six inputs, Resend code, "Verify and continue"). (2) Every submitted email receives a code; the BFF runs the lookup but reveals `recognized` / `newVisitor` only after a correct code (CR-05, D35, §5A.1). (3) The single Terms & conditions gate is replaced by the §4.5 consent ladder in the Order Summary sidebar: "I'm 18 or older" checkbox, Liability Waiver checkbox, the "By tapping **Pay $X and get my pass** …" sentence linking Pass Terms and Privacy Notice, and the Pay button; four versioned documents open in one dialog (CR-01, CR-02, D42, D43). (4) Card capture is the Pay Page embed by default in every non-test mode, wired like `PaymentPageWithPayPage`; the fixture `<select>` the review saw is gone from every demo and exists only as a labelled test-hook panel (CR-03, CR-04, D44). (5) Save card is a switch, default **off**, with the stored-credential description and "Stored card terms"; a consented save writes the token to the **prospect** wallet through the existing `saveCardToWallet` path with the consent version on the entry (CR-06, D45). (6) Mobile is required for new visitors (D37); the email field carries the transactional notice, the mobile field the SMS notice, and an unchecked "Keep me posted about joining {Club}" opt-in is recorded as its own consent event (CR-09, D32b). (7) Every generator help line is removed (CR-07). (8) A parity loop, an OTP mail sink, a sandbox-card browser policy and a simulated-user agent runner exist as documented, runnable tooling (PR-01…PR-04, D47).

**What does not change (carried from Sprint 0001, not reopened).** Route `/signup/day-pass?club=NNNNN` (→ `/signup/pass` on completion); top-level only; `OJ-PASS-SESSION` opaque cookie with the server-side `CheckoutStore`; `/api/short-term-pass` prefix; flag `oj-short-term-pass-checkout` + `onlineProspects` enforced server-side; `STP_ADAPTER_MODE=mock|platform` with production refusing mock; internal naming `ShortTermPass`; purchase order authorize → persist prospect → consented wallet write → finalize sale → issue → deliver, synchronous with `Idempotency-Key`; Pay readiness-gated not token-gated; no PAN in the React tree (static scan); BFF `erasableSyntaxOnly`; wallet identity by `(memberId, MEMBER, org)` with the owner-metadata allowlist; `STP_WALLET_WRITES` stays false until the backend sprint's dedup-key fix ships.

## Architecture

### Identify → verify state machine (CR-05)

```
BFF CheckoutRecord.state:  identify ──POST /identify──▶ challenge ──POST /verify──▶ recognized | newVisitor | identify(ambiguous)
                                ▲                         │  DELETE /identity (Change)
                                └─────────────────────────┘
UI slice.step:            identify (codeEntry=false) ─▶ identify (codeEntry=true) ─▶ recognized | newVisitor | complete
```

- `POST /checkouts/:id/identify {email}` — validates an email (`parseContact` rejects phones; a small disposable-domain blocklist in `BFF/services/shortTermPass/fixtures/disposableDomains.ts` answers 400 "Use a permanent email address."). Runs `directory.findByContact(club, 'email', normalized)` and stores `candidateMemberId` / `candidateKind` / `candidateCount` **without revealing them**. Issues a code for every valid address. Response is always `{outcome:'challenge', contact:{channel:'email', masked}, challenge:{expiresAt, resendAfter, attemptsRemaining, locked}, debug?}`; `altChannelAvailable` and the `switch-channel` action are removed (D35). The 300 ms floor stays.
- `POST /checkouts/:id/verify {code}` — on success rotates the session, then resolves the stored candidate: unique → bind member + home club, create the order shell, `{outcome:'recognized', person, contact, order}`; none → `state:'newVisitor'`, `emailVerifiedAt`, create the order shell, `{outcome:'newVisitor', contact:{channel, display, masked}, order}`; ambiguous → `state:'identify'`, `{outcome:'ambiguous', contact}`. A `newVisitor` checkout has a verified email but no bound member; `GET /wallet` still answers `NOT_VERIFIED`.
- Limits (§5A.1): `ChallengeService` send limiter 5 per `club:email` per **60 min**; identify limiter 20 per IP per **60 min**; 5 wrong attempts → `locked` plus an address-level lock (`lockedAddresses` map in the `CheckoutStore` adapter, 15 min) that also refuses `resend`; the lock and the limiters are shared across resend and re-identify.
- `POST /checkouts/:id/challenge {action:'resend'}` — schema enum shrinks to `['resend']`.
- Snapshot: `CheckoutSnapshot.step` gains nothing; `challenge` snapshot rehydrates the inline code entry.
- UI: `VerifyStep.tsx` is deleted; `IdentifyStep` renders both modes from `step === 'identify'` + `challenge` present. OTP digits stay component-local. `startOver` thunk is renamed `changeContact` (same `DELETE /identity`). `switchChannel` thunk, `SWITCH_TO_*` copy and `altChannelAvailable` are removed.

### Consent model (CR-01, CR-02, CR-09, §4.5, §5A.10)

**Catalog** — `ClubCatalogPort.getConsentDocuments(club, offer): ConsentDocumentSet` replaces `getTerms`.

```ts
interface ConsentDocument { id: 'waiver'|'passTerms'|'storedCard'|'privacy'; title: string; templateVersion: string; // e.g. "2026-09"
  html: string; meta: string; requiresAffirmativeAct: boolean; approval: 'PROPOSED'|'APPROVED'; jurisdiction: 'US' }
interface ConsentNotice   { id: 'emailTransactional'|'smsTransactional'|'marketingOptIn'; copy: string; version: string }
interface ConsentDocumentSet { tier: 'tier0'|'tier1'; documents: Record<ConsentDocument['id'], ConsentDocument>;
  notices: Record<ConsentNotice['id'], ConsentNotice>; waiverRequired: boolean; approval: 'PROPOSED'|'APPROVED' }
```

Templates live in `BFF/services/shortTermPass/fixtures/consentTemplates.ts` as functions of `{clubName, brandWord, offerName, amount, currency, visitDate}` with the v1.2 `DOCS` text as the default, a `// PROPOSED — pending counsel (CF-02)` banner in the fixture and `approval:'PROPOSED'` in every response (the UI renders a muted "Proposed terms — pending review" line in the dialog meta while `approval !== 'APPROVED'`; the capability report prints it). Per-club override: `CatalogClub.consentOverrides?: Partial<Record<id, {html, templateVersion}>>` (the existing `prospectTerms` field maps onto `passTerms`). Tier is `tier1` when `saveCard` is on, else `tier0`; the stored-card document is served regardless so the switch description can link it. `POST /checkouts` returns `consent: ConsentDocumentSet` in place of `terms`. Pass Terms are re-rendered whenever `visitDate` changes; the response carries `renderedHash = sha256(html)` per document so the browser and server can prove which text was shown.

**Order state** — `StoredOrder.terms` is replaced by:

```ts
consents: {
  adult:        { attested: boolean; at?: string }
  waiver:       { required: boolean; accepted: boolean; templateVersion: string; renderedHash: string; method?: 'checkbox'|'modal'; at?: string }
  storedCard:   { shownVersion: string; shownAt?: string }          // recorded whenever saveCard turns on
  marketingOptIn: { optedIn: boolean; version: string; at?: string }
  notices:      { emailTransactional: { version: string; shownAt: string }; smsTransactional?: { version: string; shownAt: string } }
}
saveCard: boolean   // default false
```

`PUT /checkouts/:id/order` body becomes `{visitDate?, adult?: boolean, waiver?: {accepted: boolean, method?: 'checkbox'|'modal', renderedHash: string}, saveCard?: boolean, marketingOptIn?: boolean, smsNoticeShown?: boolean}`. `order.ready = visitDate valid && adult && (!waiver.required || waiver.accepted)`. A waiver `renderedHash` that does not match the current rendering → 409 `STATE_CONFLICT` "The Liability Waiver has been updated…" (the old terms-changed rule, per document).

**Consent events** — `POST /checkouts/:id/consent-events {type:'document-opened'|'document-closed', documentId, renderedHash}` appends availability evidence; never changes order state. All events (attestation, waiver, stored-card shown, opt-in, notices, document open/close, pass-terms-by-Pay) go to `ConsentLedgerPort.append(event)` where `event = {eventId, at, checkoutId, purchaseId?, memberId?, surface:'web-online-join', type, documentId?, templateVersion?, renderedHash?, method?, copyVersion?, value?, buttonText?, clientIpHash, userAgentHash}`. `MockConsentLedger` is in-memory and inspectable (demo, tests, agents); the platform adapter is `NOT_ENABLED` (owner slot PRODUCT+LEGAL, register row). `stpLog` records `consent.recorded` with ids and versions only.

**Pass terms by Pay** — `PurchaseRequest` gains `attestation: {payButtonText: string; passTermsHash: string; privacyHash: string}`. `validatePurchase` computes the canonical text `Pay ${money(amount)} and get my pass` and the current hashes; any mismatch → 409 `STATE_CONFLICT` with `details.reason`. On `VALIDATED` the orchestrator appends the pass-terms and privacy events with `buttonText` and stores a `consents` snapshot in `PurchaseRecord.internal`. `PurchaseResult` gains `consent: {passTermsVersion, waiverVersion?, storedCardVersion?, marketingOptIn: boolean}` for the receipt.

**Wallet entry** — `CreateCreditCardInput.metadata` (new, allowlisted `['oj_storedCardConsentVersion','oj_storedCardConsentAt','oj_purchaseId']`, prefix `oj_` so nothing collides with `dt_*`) is set from `order.consents.storedCard` in `saveCardToWallet`; `MockWallet` stores it; `PlatformWallet.createCreditCard` sends it as `metadata` on the credit-card VO (the index leaf confirms entries carry a free-form metadata map read by key; acceptance by the deployed service is L3 evidence). The owner-metadata allowlist and forbidden list are unchanged; the recursive payload scan gains `oj_` keys as allowed.
