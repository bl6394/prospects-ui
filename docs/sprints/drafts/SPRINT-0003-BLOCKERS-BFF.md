## Contract notes for the UI lane

1. **`snapshot.offerId` is always set** (effective offer: the order's, else the stored selection, else `offers[0]`). `selectedOfferId` on `POST /checkouts` equals it. No need to fall back to `offers[0]` client-side.
2. **`PUT /checkouts/:id/offer`** answers exactly `{selectedOfferId, offer, consent, generation}`; refusals: 400 `VALIDATION_FAILED` "Choose one of the passes offered by this club." (field `offerId`), 409 `STATE_CONFLICT` "Start again to choose a different pass." (no `details.reason`) once an order exists or a purchase runs, 409 `STALE_GENERATION` with `details.generation` (the current one). A stored selection that left the catalog answers 409 `OFFER_UNAVAILABLE` with `details.offers` and `details.selectedOfferId` on **any** consent-rendering route (`POST /checkouts` resume included) — re-select via `PUT /offer`.
3. **Generation now bumps on every committed `PUT /order`** (and `PUT /offer`). Read `generation` from every response and send the latest; an equal-generation stale write is refused with `STALE_GENERATION`. `PUT /order` during an active purchase answers 409 `PURCHASE_IN_PROGRESS`.
4. **`order.validUntil`** is present whenever `order.visitDate` is; `order.label` and `order.durationDays` always. `receipt.{label, item, visitDate, validUntil}` on every purchase result.
5. **`pass.viewPath`** is on the creating 201 only. After reload call `GET …/purchases/:pid/pass-link` → `{viewPath, linkExpiresAt}`; 409 `STATE_CONFLICT` "This purchase has no issued pass to link to." when the pass is not issued; 404 when no credential exists (mint failed — `delivery.status` is `failed`; a `POST …/pass-link` then mints the first link).
6. **`POST …/pass-link`** → `{viewPath, linkExpiresAt, delivery}`; `delivery.status` is `sent` (SMTP / mock), `pending` (publisher) or `failed`. On `failed` the `viewPath` is the **still-valid previous** link. 429 `THROTTLED` with `retryAfterSeconds` after 3 per hour ("You have asked for the pass email a few times already. Please wait an hour."). After a resend, `GET …/purchases/:pid` reports the latest `delivery.status`.
7. **Public page (`getPassView`)**: `GET /api/short-term-pass/passes/:token` with a plain fetch (no cookie, no CSRF, no Origin). 200 = `PassView` exactly as contract §4b-5 (`club.legalName`, `club.address`, `club.links.app` are **omitted** when the club has none — Riverside has no `legalName`); `qr` is absent when `status === 'expired'`. Every other case is one identical `404 {code:'NOT_FOUND', message:"This link isn't valid.", retryable:false, correlationId}`; 429 `THROTTLED` after 60 requests per IP per 15 minutes. The `<noscript>` image is `GET /api/short-term-pass/passes/:token/qr.png` (404 once expired).
8. **`/signup/pass/pv1.…` documents** are now served by the SPA entry (PA-1 fixed) without the AppDynamics snippet and without a flag hint (`window.featureFlags.oj_short_term_pass_checkout` is `false` there — do not gate the page on it).
9. **Outbox (`GET /testing/outbox`)** `kind:'pass'` messages carry `label`, `validUntil`, `viewPath` (raw link). The done-page smoke can read the link there or from the 201.
10. Kelly's masked contact is `m•••@m.com` (three dots), Jordan's `j•••••@email.com`.

## Answers to the UI lane's seven contract questions (`SPRINT-0003-BLOCKERS-UI.md`)

1. **`GET …/pass-link` after reload — confirmed.** Ownership is "same checkout id" first (`purchase.checkoutId === record.id`), so the cookie rotation at verify is irrelevant; the resumed `complete` checkout resolves to the same record. `requireVerified` needs `boundMemberId` + `emailVerifiedAt`: a recognized checkout has both from verify; a **new visitor's** checkout is bound at `PERSON_PERSISTED`, so after a COMPLETE purchase the reload works too — pinned in `passes.test.ts` (revoke block, "UI question 1"). Edge: a new visitor whose purchase FAILED before `PERSON_PERSISTED` (decline) gets 401 `NOT_VERIFIED` rather than 409 — there is no pass to link to either way.
2. **`POST …/pass-link` with `delivery.status:'failed'` — confirmed.** The response is `{viewPath: <old, still valid>, linkExpiresAt: <old>, delivery: {status:'failed', channel, masked}}`; `linkExpiresAt` is always present (`purchase.test.ts` U19 failed-transport case asserts the full object). No re-fetch needed; `GET …/pass-link` returns the same old link.
3. **`PUT /offer` in state `verified` — confirmed.** `retryLookup` goes through the same `commitOrderShell` as verify: the selection is read inside the committing `CheckoutStore.update`; a selection that lands during the lookup is the one the order uses, and once the order exists `PUT /offer` answers 409 (`offer.test.ts` "offer vs retryLookup").
4. **`generation` on `PUT /offer` — confirmed.** The commit bumps it and the `OfferResponse.generation` is the new value; the next `PUT /order` with that value is accepted. Note the symmetric rule: every committed `PUT /order` also bumps it, so always take `generation` from the latest response (`order.test.ts` P1-4 pins an equal-generation write refused with `STALE_GENERATION`).
5. **404 / 429 on `GET /passes/:token` — fine.** Any 404 is the single `{code:'NOT_FOUND', message:"This link isn't valid."}` body. The 429 is the standard envelope `{code:'THROTTLED', retryable:true, retryAfterSeconds}` plus `Retry-After`; showing it as generic + "Try again" is acceptable for this sprint (60 per IP per 15 min is generous for a person; the smoke resets it via `POST /testing/reset`).
6. **`PassView.club.links` — confirmed `{app?}` only**, and `app` is omitted (not `undefined`) when the club has none; `legalName` and `address` are omitted the same way (Riverside has no `legalName`). The key set is pinned in `passView.test.ts`; `website` is not sent.
7. **Receipt `item` — confirmed.** `lineItemOf(label, offerName)`: Core "3-day pass · Gym Floor"; Riverside exactly "1-day pass" (offer name equals the label, so it reads once). `PurchaseResult.receipt.item` and `PassView.receipt.item` carry the same string (`purchase.test.ts` U11, `passes.test.ts` U15).

E2 note from the UI file, confirmed on the BFF side: the page's `<noscript>` PNG and the smoke's decode target is `GET /api/short-term-pass/passes/<token>/qr.png`; it answers 404 once the pass is `expired` while the page still shows the dates.
