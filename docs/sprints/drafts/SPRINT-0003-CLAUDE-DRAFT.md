## Architecture

### Offer selection (CR-10, OQ-1)

```
POST /checkouts            → offers[] (catalog order; [0] is the default), snapshot.offerId
PUT  /checkouts/:id/offer  {offerId, generation?}  allowed while state ∈ {identify, challenge, verified}
                           → {offerId, offer, consent, generation}      (409 once an order exists)
POST /verify               → createOrderShell(catalog, club, record.selectedOfferId ?? offers[0])
PUT  /order, POST /purchases, POST /checkouts(resume) → consentSetFor(catalog, club, order.offerId, visitDate, now)
```

- `CheckoutRecord.selectedOfferId?: string` — set by the new route, kept by `resetIdentity` (Change), cleared by revoke (Start again creates a new checkout anyway). `buildSnapshot` exposes it as `snapshot.offerId`; the UI restores the checked card on reload.
- `requireOffer(catalog, club, offerId?)` resolves the named offer or the first; `consentSetFor` and `validatePurchase` take the **order's** `offerId`; `buildCheckoutResponse` renders `consent` for `record.order?.offerId ?? record.selectedOfferId ?? offers[0]`. A test pins that a Core checkout with the 3-day pass selected never renders a 1-day Pass Terms sentence anywhere (fact 1).
- Selection does not bump `generation` (like order edits) but carries `generation?` for the stale check. Because the order does not exist yet, no consent re-pricing of a live order is needed; the waiver and adult attestations are unaffected. Changing the pass after verify = Change (re-identify, selection kept) or Start again (new checkout, default offer). This is v4's behaviour; re-pricing a live order is recorded as not built.
- `OfferSummary` gains `label` ("1-day pass"), computed server-side from `durationDays` so the UI and the templates never disagree; `CatalogOffer.provisional?: boolean` marks CF-04 prices in the fixture and the capability report only.

### Validity model (CR-11, CR-17, OQ-2)

- `validUntil = addDays(visitDate, durationDays − 1)`, calendar days, club-local, inclusive of both ends (v4 `validityLabel`; FR-P5/FR-P6 calendar assumption — CF-05 records the hours alternative and Q19's maximum). Computed in `createOrderShell` and re-computed by `applyOrderUpdate` on every `visitDate` change; `maxVisitDate` stays per-offer (`maxDaysAhead`), and a kept date past the new maximum resets to today.
- Carried on `StoredOrder`, `OrderSummary` (`durationDays`, `label`, `validUntil`), `FinalizeSaleInput` and `IssuePassInput` (`validUntil`), `IssuedPass` and `PurchaseResult.pass` (`validUntil`, `label`), `DeliveryInput`, the mock QR payload (`STP2|passId|club|visitDate|validUntil|sig`, sig over all fields + receipt) and `PassView`.
- One label function on each side, pinned against the same fixtures: 1-day → `dayLabel` ("Today · Wed, Sep 9" / "Wed, Sep 16"); multi-day → `"{Today|Wed, Sep 16} – {Fri, Sep 18}"` (en dash U+2013 with spaces, v4 line 403–405). BFF `validityLabel(visitDate, validUntil, todayIso)` in `consentTemplates.ts` (also used by the email); UI `validityLabel` in `format.ts` (sidebar help, Valid row, pass block, pass page). Date-input label: `durationDays === 1 ? 'Day pass applies on' : 'Pass starts on'`.
- Pass Terms template: `"{label} to {legalName}, valid {validity}. Price {amount} including tax. One-time purchase — no membership, no renewal, no recurring billing."`; `TemplateContext` gains `offerLabel`, `validity`; `CONSENT_TEMPLATE_VERSIONS.passTerms = '2026-09.2'`; refund paragraph unchanged (PRD D15/D22, approved delta AD-09). `renderConsentDocumentSet` computes `validUntil` from `offer.durationDays`, so `renderedHash` and `consentRevision` already follow price and validity — no new revision input.

### "View your pass" token, routes and page (CR-13, OQ-4)

- **Token:** `newOpaqueId('pv_')` (192 random bits, base64url); stored only as `HMAC-SHA256(STP_SESSION_SECRET, token)` on `PurchaseRecord.passView = {tokenHash, issuedAt, linkExpiresAt, revokedAt?, rotations}`; `PurchaseStorePort.findByPassTokenHash(hash)`. Minted at the `ISSUED` checkpoint so the delivery step can put it in the email. The raw token leaves the BFF exactly three ways: the email, `pass.viewPath` on the **creating** `POST /purchases` 201 (attached by the route from `executePurchase`'s transient return, never written to `result`), and the `pass-link` response. `GET /purchases/:pid`, `/testing/state` and logs never carry it. Rationale over a signed JWT: revocable by rotation, no key management or claim parsing, same posture as the hashed session key.
- **Lifetime:** `linkExpiresAt` = club-local end of `validUntil` + `STP_PASS_LINK_GRACE_DAYS` (default 7; CF-06 decides the final number). Valid before the start date so a buyer can open tomorrow's pass today.
- **Public routes** (`BFF/routes/shortTermPass/passes.ts`, mounted on the same router, **no** `checkoutChain`): `GET /passes/:token` and `GET /passes/:token/qr.png`. Chain: `pipeline(rateLimit(passLimiter, ip), loadPass(deps), gateForPass(deps), handler)` — token shape check → hash → lookup → revoked/unknown 404, expired 410 → `requireShortTermPass` with the purchase's club (flag + `onlineProspects`, fail closed) → response. `no-store`, `X-Correlation-Id`, no cookie read or set, GET only (no CSRF or Origin, as on every read). `passLimiter = new WindowLimiter(60, FIFTEEN_MINUTES_MS)` per IP; a per-token limiter (10/min) throttles scraping of one link.
- **`PassView`** is built by `services/shortTermPass/passView.ts` from the purchase record, the club and `now`: `status` by club-local today vs `visitDate…validUntil`; holder = first name only; masked email from `internal.contact.masked`; no member id, purchase id, checkout id, token, PAN or full email (key-set leak scan in tests).
- **Resend / rotate:** `POST /checkouts/:id/purchases/:pid/pass-link` on the owning checkout (`requireVerified`, `loadOwnedPurchase(allowVerifiedMember)` as `wallet-retry`) — revokes the current hash, mints a new token, calls `delivery.deliver` again, answers `{viewPath, delivery}`; `WindowLimiter(3, ONE_HOUR_MS)` per purchase. This is CF-06's "resend path" and the buyer's recovery when `delivery.status` is `failed` (the QR is no longer on the page).
- **Hooks-only:** `POST /testing/passes/revoke?checkoutId=&purchaseId=` marks the current token revoked so the smoke can prove a 404 without waiting for expiry; `/testing/outbox` shows `viewPath` per message.
- **UI page:** `PAGES.passView = '/pass/:token'`; `App.tsx` checks `matchPath(pathname, {path: PAGES.passView, exact: true})` **before** the `/day-pass` / `/pass` branch (fact 8; `isPathWithin('/pass/x', '/pass')` would otherwise swallow it). `routes/ShortTermPass/PassViewPage.tsx` has no Redux dependency: local state, `services/shortTermPass.getPassView(token)`, renders `CheckoutShell` (brand, static location, "Secure checkout" → "Your pass" is not needed; header unchanged) with `sidebar={<PassReceipt view={…}/>}` and main `<PassCredential view={…}/>`; the `.qr` styles move from the done page to this component. No `?club=` and no flag hint: the API gate is the authorization. `/signup/pass/<token>` is served by the existing history fallback (Accept `text/html`).

### Done page and receipt (CR-12, OQ-5)

`PassBlock` drops the `.qr` block and `qrcode.react`; props become `{label, validity, delivery, viewPath?, onResend}`. Sentence table: `sent` → v4 text verbatim; `pending` / `failed` → the truthful variants in U12 (approved deltas); `not-attempted` → "Show your name at the front desk." The "View your pass" link renders when `purchase.pass.viewPath` is in the slice (creating response); otherwise "Resend pass email" → `resendPassEmail` thunk → `POST …/pass-link` → toast "Pass email sent to {masked}" and the new `viewPath` in state.
