### Position on Open Question 2 — home and repo (D60, CF-11, CR-27)

**Recommendation: keep the code in `online-join-ui` + `online-join-bff` and serve it at a standalone Guest Pass host; do not fork MICO.** D60's rationale was "a branch off OJ would inherit the membership model" and "OJ's day pass is a membership plan that expires in a day". The merged build never touched the membership model: it is its own route (`/signup/day-pass`), its own shell (`CheckoutShell`), its own BFF router (`/api/short-term-pass`), its own stores and consent set. What D60 actually asks for — a standalone URL a club can put behind a "Buy a day pass" button, not inside the join funnel — is a **hosting** change, not a repo change: one more host on the existing ingress (`guestpass.dev.abcfitness.net`, later `guestpass.abcfitness.com`), host-scoped routing in the BFF so `/` on that host serves the Guest Pass entry document and the membership routes answer 404 there, the origin allowlist and the LD flag scoped to the club. "This page could become the new OJ" is better served by the React + Koa stack, which *is* the split-out OJ, than by a Java monolith whose web tier is jQuery/steal.js. **CF-11 answer: repo home = the two online-join repos; the standalone URL is a helm + BFF change (Phase D).** Chancy's guidance "like Myko" is honoured where it matters — the DT read path (below).

*Cost this sprint (recommended):* ~2 days — BFF host-scoped router + entry document (~1 day), helm PR with the host, TLS entry, `STP_ALLOWED_ORIGINS`, key removals (~0.5 day, signed commit per the helm-configs rule), Cloudflare rule request and LD flag creation (tickets to PK / platform, ~0.5 day of coordination). Reversible: removing the host entry restores today's layout.

*Alternative A — fork a Guest Pass page off MICO (Java/Spring, `/iclub`):* a new Spring MVC controller + JSP/steal.js page, and a port of the OTP challenge, session cookie, consent set with hashes, Pay Page embed, idempotent purchase orchestration and the mock/test seams to Java — roughly 6–10 engineering weeks, the loss of ~1,400 passing tests across the two repos, a second Pay Page integration to certify, Sonar Java rules, and MICO's release cadence (D55 notes the one-release-a-day constraint on the DT side). It is the *larger* step towards "the new OJ" because it re-enters the monolith we are leaving.

*Alternative B — new repos `guest-pass-ui` / `guest-pass-bff` seeded from the OJ code:* ~1 week of extraction plus CI, Harbor/Artifactory publishing, helm charts, Sonar projects and LD projects, then two more repos to keep in step with `@abc/bff-toolkit` and the design system. This is the right *later* step if the product grows past a checkout (D60's "new OJ"); record it as the v2 home decision, not this sprint.

*If the decision is still open at kickoff:* build host-agnostic. Phase C adds the `/guest-pass` path alias next to `/signup/day-pass`; Phase B's host-scoped routing reads `STP_STANDALONE_HOSTS` (empty = today's behaviour). Only Phase D's helm/Cloudflare tasks wait; nothing in A–C or E does.

### Position on Open Question 3 — DT read path (D64, CR-31)

**Recommendation: read through datatrak-service, exactly the layer MICO uses (fact 1).** New platform adapter `DatatrakServiceCatalog` implements `ClubCatalogPort`: `resolveClub` → `GET /external/club/getClubDefaultExternal.spr` (club name, `onlineProspects`, `prospectTerms`, and the new **waiver language** field from Chancy's DT PR), `getOffers` → `GET /external/pos/saleItems.spr` filtered to items carrying the new **`guestPassOnline`** flag with **`contractDays`** and **`visits`** (price from `catalogPrice`, `taxed`), consent documents rendered from the club's terms and waiver text. Same basic-auth credential MICO's `orasvc-client` uses (secret via `envsecretRefs`), in-cluster URL `http://datatrak-service:8080/external` (dev ingress `datatrak-service.dev.abcfitness.net` for local runs), 5-minute cache as today's `PlatformClubCatalog`. This satisfies D64's "no enterprise-API change" (the enterprise API is `eapi`, `club-resource.url`; datatrak-service is the DT team's own service layer) and puts the new columns behind Chancy's PR, where the DBA columns already land.

*Preconditions (registered, not blockers):* CF-13 — Chancy's PR must surface the three catalog-item columns and the waiver text in the two `.spr` responses (if it does not, the smallest change is three fields on `SaleItem` and one on `ClubDefaultExternal` in the same PR, reviewed by PK — D69); CF-14 — `pos/saleItems.spr` must answer for a club with an empty `memberId` (MICO passes the session member's id; the Guest Pass page has no member before purchase); a time-boxed A4 probe against the dev host settles both.

*Feasible in dev this sprint?* Yes for the adapter and its recorded-response tests; live only once CF-13/CF-14 hold and the credential is in the `platform-online-join-bff` secret. Until then `STP_CATALOG_SOURCE=fixture` (default in mock mode) keeps the deterministic fixtures, and `STP_CATALOG_SOURCE=datatrak` is a dev-only switch that fails closed (`NOT_ENABLED` per club) when the response lacks the fields.

*Fixture shape until the DBA columns exist:* `CatalogOffer {offerId (= saleItemId), name (= catalogItemName), amountMinor, currency, taxed, contractDays, visits, guestPassOnline: true, perks?}`; `CatalogClub` gains `waiverText?`. Recorded datatrak-service responses (XML samples Chancy can paste) live under `STP/fixtures/datatrak/*.xml` so the adapter's mapper is unit-tested against the wire format before the service exists.

*Alternative A — direct Oracle from the BFF:* `oracledb` client in a Node image, DB credentials in the OJ namespace, a network path from EKS to the DT Oracle (security review), the VPD context call before every query (`vpdsecurity.set_datatrak_ctx`, per `datatrak-data-access.md`), and schema knowledge of the catalog-item table that is in no repo we hold — 4–6 days plus approvals, and a database coupling a BFF should not carry. *Alternative B — a MICO `/iclub` endpoint:* MICO would itself call datatrak-service, so this adds a hop and a MICO release without removing any dependency. *Alternative C — wallet-account-sync's Oracle access:* wrong owner (the wallet team is already reviewing our prospect lane critically — `concerns.txt`) and wrong data (it maps members and payment methods, not the catalog).

## Architecture

### 1. Catalog model and DT read path (D61, D64, D70, D72; CR-28, CR-31)

```
ClubCatalogPort
  resolveClub(clubNumber)  → CatalogClub {…, onlineProspects, prospectTerms?, waiverText?}
  getOffers(clubNumber)    → CatalogOffer[] {offerId, name, amountMinor, currency, taxed, contractDays, visits, guestPassOnline, perks?}
  getConsentDocuments(club, offer, {todayIso}) → ConsentDocumentSet (passTerms from club terms or template; waiver from club text or template; marketing document)
adapters
  mock/catalog.ts                    fixtures (STP_CATALOG_SOURCE=fixture, default in mock mode)
  platform/catalog.ts                today's MICO getClub for club data + fixture offers  → kept as `mico` source for one sprint (fallback)
  platform/datatrakServiceCatalog.ts NEW: /external/club/getClubDefaultExternal.spr + /external/pos/saleItems.spr (STP_CATALOG_SOURCE=datatrak)
```

- **v1 filter** (`STP/order.ts requireOffers`): only items with `guestPassOnline && visits === 1 && contractDays >= 1 && amountMinor > 0` are offered; skipped items are listed in the capability report and logged once per cache fill. `OfferSummary` to the browser: `{offerId, name, amountMinor, currency, contractDays, visits, validityLabel}` — `validityLabel` computed server-side ("One time use only, valid today" / "…valid for N days"); `label` is the catalog name (no "1-day pass" synthesis).
- **Never hard-coded:** contract days, visits, price, terms and waiver come from the port; `validity.ts` has no constants except the copy templates; the UI renders what the contract carries (D71).
- **Consent from DT:** `prospectTerms` → `passTerms` override (already); `waiverText` → `waiver` override with `templateVersion: club-<sha256(waiverText).slice(0,8)>`; a club with no waiver text falls back to the PROPOSED US template (CF-18 asks whether it should instead be optional).
- **datatrak-service adapter:** Feign-equivalent `fetch` with basic auth (`STP_DT_SERVICE_URL`, `STP_DT_SERVICE_AUTH` via `envsecretRefs`), XML parsed with a small mapper (`fast-xml-parser`, one new dependency) against recorded fixtures `STP/fixtures/datatrak/{clubDefaultExternal,saleItems}.xml`; 5-minute cache per club; missing fields → the club is `NOT_ENABLED` for guest passes (fail closed, capability note). The item id sent on the create call and the sale is `saleItemId`.

### 2. Validity model (D48, D62, D71, D72)

- `beginDate` = club-local calendar day of the **purchase** (computed inside `validatePurchase` from `deps.now()` and `club.timezone`, not at order-shell time); `expirationDate = beginDate + contractDays − 1` (inclusive, club-local; a 1-day item expires the same day — D48); `visits = offer.visits` (1 in v1). `useBy` on the order is the same computation from today, for display; a midnight rollover between render and Pay changes `consentRevision` (it binds `useBy`) and is refused with 409 `CONSENT_REVISION` — the buyer re-taps Pay and sees the new date.
- `STP/validity.ts` keeps `addCalendarDays`, `shortDateLabel`, `clubLocalToday`; deletes `validUntilOf(visitDate, durationDays)`, range `validityLabel`, `dateFieldLabelOf`, `linkExpiresAtOf`; adds `expirationDateOf(beginDate, contractDays)`, `useByLabel(contractDays, useBy, todayIso)` → "One time use only, valid today · Thu, Sep 17" / "One time use only, valid for 7 days — use by Wed, Sep 23". The UI's `format.ts` mirrors it and both are pinned on identical fixtures.
- Access is enforced by DT from the prospect's begin/expiration/visits (D48/D62); the page and the BFF build no door logic, no QR payload, no link-use counter.

### 3. Purchase order and compensation (D65, CR-32, CR-06, CR-12, PR-14)

```
VALIDATED → PERSON_PERSISTED → AUTHORIZED → WALLET_RESULT → SALE_FINALIZED → COMPLETE
                 │                 │(declined / unknown / throws)
                 │                 └→ compensate: created ? deactivate(memberId) : restore(memberId, previousAccess)
                 │                        ok → FAILED {failure.step:'authorize', person.deactivated|restored:true}
                 │                        fails ×3 → RECONCILING {failure.step:'deactivate'|'restore'} + log prospect.compensate-failed
                 └(create/repaint throws) → FAILED {failure.step:'persist-person'}; nothing authorized
```

- `ProspectPort` v4: `create(input: CreateProspectInput, idempotencyKey) → {outcome:'created', memberId, homeClub, barcode?} | {outcome:'conflict', existingMemberId}`; `repaint(memberId, access: ProspectAccess, idempotencyKey) → {previous: ProspectAccess}`; `deactivate(memberId, idempotencyKey) → {status:'inactive'|'already-inactive'}`; `restore(memberId, access, idempotencyKey)`. `CreateProspectInput` gains `beginDate`, `expirationDate`, `visits`, `marketingOptIn`, `saleItemId`, `walletToken?` (D62: the create call carries the wallet token; the wallet *entry* is still written only after a successful auth, D65). `ProspectAccess = {beginDate, expirationDate, visits}`. The mock directory persists `access` per person so repaint/restore are observable in `/testing/state`.
- **Idempotency.** The purchase record stores `internal.memberId`, `internal.personCreated`, `internal.previousAccess` at `PERSON_PERSISTED`; a replay after a crash between create and authorize never creates a second prospect (the directory lookup after OTP already bound returning buyers; for new visitors the mock create is keyed by `purchaseId`, and the platform adapter re-reads by email before creating — CF-15 asks whether `addProspect.spr` is itself idempotent). Compensation is idempotent by `memberId` + `purchaseId`.
- **Payment vs sale in DT terms.** In the platform, `pos/onlineSale.spr` is both the charge and the sale; the orchestrator keeps `AUTHORIZED` and `SALE_FINALIZED` as separate checkpoints so the mock, the compensation and the result stay truthful; a platform adapter may implement `PaymentPort.authorize` as the online sale and `PassSalePort.finalizeSale` as a record-only step — noted in the adapter register, decided when Mark's API package lands.
- **`ISSUED` and `mintPassLink` are removed.** `pass` on the result is derived from the persisted access: `{status:'issued', label, beginDate, expirationDate, visits}`; `IssuePassInput`/`IssuedPass`/`qrPayload` leave the port. `PassSalePort` shrinks to `finalizeSale`.
- **Delivery.** `DeliveryPort.deliver` runs only in mock mode (stand-in email, U20); platform mode records `delivery = {status:'delegated', renderer:'dt', channel:'email', masked}` — DT sends the prospect email with the QR and the POS receipt (D52, D63). `PurchaseResult.delivery.renderer: 'dt'|'mock'` is new; the UI copy is v6 for `delegated` and `sent`.
- **Attempt logging, not persistence (D65).** One `purchase.attempt` line per authorization outcome: `{club, purchaseId, checkoutId, outcome, declineCode?, brand?, last4?, ipHash, uaHash, correlationId}`; never PAN, token or email. Purchase results stay in the in-memory store as today (L4 register row unchanged).
- **Rate limiting.** `WindowLimiter(10, ONE_HOUR_MS)` per IP on `POST /purchases` (U23); the Cloudflare rule on the standalone host is PK's (gated pilot step, D65 "as on OJ").
- **Webhook propagation (PR-14).** The BFF cannot observe DT webhooks; it logs `prospect.created` / `prospect.deactivated` / `prospect.restored` with `memberId` and `correlationId` so Chancy and Kyle can correlate the deactivate in the CRM logs during the gated check. Written as pilot gate V-P2 with owners, not as a BFF test.
