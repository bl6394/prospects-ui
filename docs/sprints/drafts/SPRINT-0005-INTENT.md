# Sprint 0005 Intent: G1 — the guest-pass fields through the DataTrak service layer, with every production DB dependency behind a feature flag

## Seed

> In the context of the DT-21555 handoff review (artifact `DP7MTDcf8QFNS9dJk4c3Px`, finding **G1 "The web-service layer is not in the handoff"**): implement G1 — make sure that anything that requires a DB change in production sits behind a feature flag. Do the sprint planning for this.

G1 as written in the review: *"The scripts add columns, but nothing exposes them through the DataTrak service endpoints the Guest Pass page reads, the same layer MICO uses. The page needs, per sale item, the guest-pass flag, contract days and visits; per club, the liability text beside the prospect terms and the club timezone, which exists in no table today. Until those fields appear on the responses, dev runs on synthetic fixtures and the live catalog read stays blocked. **Ask:** add the three sale-item fields and the liability field to the sale-items and club-defaults responses in the same DataTrak change, add a timezone, and confirm the field names."*

The seed adds a governing rule on top of the ask: **every code path, in every repo, that depends on the new production columns (`CATALOGITEMS.CGI_GUEST_PASS*`, `SALEITEMS.SAI_GUEST_PASS*`, `SPL_EXTENSIONS.SPLEX_PROSPECT_LIABILITY`) or on the new `ADD_GUEST` template rows must sit behind a feature flag**, so that (a) application code can deploy before the DBA runs the scripts without breaking anything, (b) the scripts can be rolled back while the code stays deployed, and (c) exposure is switched per environment and per club, not by a release.

## Constraints

## Open Questions

Questions the drafts should try to answer (and the interview will settle):

1. **DTO strategy for `ClubDefaultExternal`.** The class is in a shared interface jar. Bump the jar (another repo and release cycle), subclass locally (`ClubDefaultExternalV2` / a wrapper with `@JsonUnwrapped`), or add a sibling object on the response (`club.guestPass {…}`)? Which is least risky for MICO's XML path?
2. **Flag granularity and naming.** One flag per repo (`datatrak-service-DT-21555-guest-pass-fields`, `datatrak-DT-21555-guest-pass`) or one shared key evaluated by both? Club context, VPD context, or global? Who creates them in LD dev/prod and what are the defaults?
3. **Delivery into Chancy's PR.** PR onto `feat/NOJIRA-guest-pass-email`, a stacked follow-up PR, or a written change request only? The drafts should cost each.
4. **G2 inside G1?** The member-id requirement is in the same controller/validator. Make `memberId` optional when the flag is on (returning items without the appointment enrichment), add a sibling club-scoped endpoint, or leave G2 to a later sprint?
5. **Timezone format.** Emit `TZL_ABC_CODE` as-is (it is already a Java zone id) or normalise to IANA and validate with `ZoneId.of`? What does the BFF do with an unknown id (today: fail closed)?
6. **Liability text size/format (G8).** Keep `VARCHAR2(4000)` with a UI limit and base64-HTML on the wire, or CLOB? This sprint only has to pick the wire convention; the column type is Terry's.
7. **Rollout ownership.** Who runs the scripts in dev and when (Terry); who flips the DT dev flag (Chancy/PK); who adds `STP_DATATRAK_SERVICE_AUTH` to the BFF secret (PLATFORM)? Dates become register rows.
8. **Verification of "byte-identical when off".** Golden-response tests against recorded JSON/XML, or SQL-string assertions on the DAO, or both?
